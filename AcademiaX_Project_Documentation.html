2. Abstract

AcademiaX is an enterprise-grade distributed software system designed to automate academic administration in higher-education institutions. Traditional university management portals often suffer from performance degradation, single points of failure, and scalability bottlenecks during peak academic events such as semester course registration and tuition settlement.

To solve these real-world challenges, AcademiaX decomposes administrative operations into seven autonomous microservices:

  1. Eureka Server (8761) – Centralized service discovery registry.
  2. API Gateway (8080) – Reverse proxy, client entry point, and perimeter JWT security enforcer.
  3. Auth Service (8081) – BCrypt credential management and 7-day cryptographic JWT token generation.
  4. User Service (8082) – Comprehensive student and faculty profile management.
  5. Course Service (8083) – Course catalog definition and seat capacity allocation.
  6. Enrollment Service (8084) – Core business orchestration engine validating course eligibility and seat limits.
  7. Payment Service (8085) – Tuition fee invoice generation and transaction state management.

Built with Java 25, Spring Boot 4.1.1, Spring Cloud 2025.1.3, and PostgreSQL 18, AcademiaX implements the Database-per-Service pattern, Declarative REST communication via Spring Cloud OpenFeign, stateless JSON Web Token (JWT) security, and client-side load-balanced routing using Spring Cloud Gateway Server Web MVC. The system ensures high availability, automated seat capacity enforcement, and seamless end-to-end tuition processing.

3. Problem Statement

Higher education institutions face operational and technical difficulties during registration windows:

  1. Course Information Disorganization: Course offerings, credit units, and instructional faculty details are often managed in disconnected spreadsheets or legacy monolithic databases.
  2. Enrollment Overbooking: High-demand courses encounter over-enrollment due to lack of real-time transactional concurrency checks on classroom capacity.
  3. Enrollment Status Desynchronization: Students register without immediate validation of prerequisite availability or registration state tracking.
  4. Disconnected Tuition Billing: Enrollment and student accounts are often separate silos, resulting in manual fee ledger entries, lost revenue, and reconciliation delays.
  5. Monolithic Vulnerability & Downtime: When thousands of students log in concurrently, monolithic architectures experience complete site-wide outages; a failure in billing knocks down course browsing and profile viewing.
  6. Authentication & Insecure Boundaries: Absence of a unified perimeter security mechanism leaves internal CRUD endpoints vulnerable to unauthorized data tampering.

4. Objectives

The primary objectives of the AcademiaX project are:

  1. Decoupled Architecture: Structure the platform into modular, independently deployable microservices organized around distinct business domains.
  2. Perimeter Security & Stateless Authentication: Implement an API Gateway that strictly validates JSON Web Tokens (JWT) using HMAC-SHA256 signatures before forwarding requests to internal services.
  3. Dynamic Service Discovery: Eliminate hardcoded IP addresses/ports using Netflix Eureka, allowing services to locate each other dynamically by logical service names.
  4. Real-Time Capacity Enforcement: Ensure students cannot enroll in full courses by enforcing real-time transactional capacity checks through declarative Feign clients.
  5. Automated Tuition Invoicing: Automatically initiate a $500.00 pending tuition record in the Payment Service upon every successful course enrollment.
  6. Isolated Persistence (Database-per-Service): Provide dedicated PostgreSQL databases for Auth, User, Course, Enrollment, and Payment services to enforce data autonomy.
  7. Standardized REST APIs: Expose predictable, RESTful endpoints across all services supporting complete CRUD operations.

5. Existing System & Limitations

In a traditional academic management system (Monolithic Architecture):

  • Single Monolithic Codebase: All business logic (user profiles, course catalog, registration, and billing) lives in one giant application deployed as a single archive.
  • Shared Database Bottlenecks: A single centralized database handles all reads and writes. A long-running financial report or student roster export locks database tables, stalling student registrations.
  • Single Point of Failure (SPOF): A bug or high memory usage in the payment module crashes the entire university portal.
  • Tight Coupling & Slow Deployment: Changing a field in the User module requires retesting, recompiling, and redeploying the entire university portal.

6. Proposed System (AcademiaX Solution)

AcademiaX overcomes these limitations by adopting an Enterprise Microservices Architecture:

[ Traditional Monolith ]                      [ AcademiaX Microservices ]
+----------------------+                      +-------------------------------+
| User Management      |                      | User Service       (Port 8082)|
| Course Management    |   Transformed Into   | Course Service     (Port 8083)|
| Course Registration  |  =================>  | Enrollment Service (Port 8084)|
| Payment & Billing    |                      | Payment Service    (Port 8085)|
| Shared Monolith DB   |                      | Auth Service       (Port 8081)|
+----------------------+                      +-------------------------------+
                                                + Separate Databases for Each!

Key Advantages:

  • Resilience: If the Payment Service is temporarily offline or under heavy batch processing, students can still browse courses and view profiles.
  • Per-Service Scaling: The Enrollment and Gateway services can be scaled independently during registration week without scaling the rest of the application.
  • Domain Autonomy: Each team can develop, test, and package their microservice independently.
  • Robust Security Perimeter: All inbound requests are checked once at the Gateway, protecting backend services from unauthorized access.

Component Roles:

  1. Eureka Server (8761): Acts as the phonebook for microservices. Every microservice registers its IP, port, and status (UP).
  2. API Gateway (8080): The single exterior front door. Evaluates every request's JWT header and routes to the appropriate service using Eureka service IDs (lb("SERVICE-NAME")).
  3. Auth Service (8081): Issues 7-day cryptographic JWTs upon successful username and BCrypt password verification.
  4. User Service (8082): Maintains institutional records of students and instructors.
  5. Course Service (8083): Maintains course names, assigned instructors, and strict seat quotas.
  6. Enrollment Service (8084): Coordinates student registrations. Uses OpenFeign to check Course capacity and triggers Payment fee generation.
  7. Payment Service (8085): Manages tuition records, fee balances, and payment statuses (PENDING, COMPLETED).

9. Eureka Service Discovery

What is Eureka?

Netflix Eureka is a REST-based registry service designed for microservices architectures. In distributed systems, services may scale dynamically, run on arbitrary ports, or change IP addresses.

Why is Eureka Needed?

Without Eureka, the API Gateway and services would have to hardcode URLs like http://192.168.1.50:8082/users. If that IP or port changes, the entire system breaks. With Eureka:

  • Every microservice announces itself by its application name (e.g., USER-SERVICE).
  • The API Gateway simply routes to lb("USER-SERVICE"), delegating host/port lookup to Eureka.

Registration and Discovery Workflow:

  1. Startup: When user-service starts up, its Eureka Client contacts http://localhost:8761/eureka and registers USER-SERVICE.
  2. Heartbeats: Every 30 seconds, running services send heartbeats to Eureka to keep their lease active.
  3. Dashboard Meaning of "UP": On the Eureka Web Console (http://localhost:8761), status UP (1) indicates that an instance is healthy, reachable, and ready to accept traffic.
Registered Applications on Eureka Dashboard:
- API-GATEWAY        : 192.168.x.x:api-gateway:8080        (Status: UP)
- AUTH-SERVICE       : 192.168.x.x:auth-service:8081       (Status: UP)
- USER-SERVICE       : 192.168.x.x:user-service:8082       (Status: UP)
- COURSE-SERVICE     : 192.168.x.x:course-service:8083     (Status: UP)
- ENROLLMENT-SERVICE : 192.168.x.x:enrollment-service:8084 (Status: UP)
- PAYMENT-SERVICE    : 192.168.x.x:payment-service:8085    (Status: UP)

10. API Gateway

The API Gateway runs on port 8080 using Spring Cloud Gateway Server Web MVC.

Key Functions:

  1. Single Entry Point: All clients interact exclusively with http://localhost:8080.
  2. Load-Balanced Routing: Evaluates the request path prefix and forwards requests via Spring Cloud LoadBalancer:
    • Path /auth/** $\rightarrow$ AUTH-SERVICE
    • Path /users/** $\rightarrow$ USER-SERVICE
    • Path /courses/** $\rightarrow$ COURSE-SERVICE
    • Path /enrollments/** $\rightarrow$ ENROLLMENT-SERVICE
    • Path /payments/** $\rightarrow$ PAYMENT-SERVICE
  3. Perimeter Security Enforcer: Intercepts requests, validates incoming JWT tokens, and blocks unauthorized traffic before routing to downstream microservices.
  4. Gateway Controller Endpoints: Exposes lightweight verification endpoints:
    • GET /gateway $\rightarrow$ Returns "AcademiaX API Gateway is running"
    • GET /gateway/status $\rightarrow$ Returns "AcademiaX API Gateway is healthy"

11. JWT Authentication & Security Model

AcademiaX implements stateless security using JSON Web Tokens (JWT) and Spring Security.

Anatomy of an AcademiaX JWT:

An AcademiaX token consists of three base64url-encoded parts separated by periods (.):

  1. Header: Specifies the cryptographic algorithm (HS256 / HMAC-SHA256) and token type (JWT).
  2. Payload (Claims):
    • sub: The subject/username (e.g., "student_john").
    • role: The authorized academic role (e.g., "STUDENT", "ADMIN").
    • iat: Issued-at epoch timestamp.
    • exp: Expiration epoch timestamp (7 Days validity = 604,800,000 ms).
  3. Signature: Cryptographic signature generated with the server secret key (AcademiaXSecretKeyForJWTAuthentication2026).
[ Header: {"alg":"HS256","typ":"JWT"} ] . 
[ Payload: {"sub":"student101","role":"STUDENT","iat":1790000000,"exp":1790604800} ] . 
[ Cryptographic HMAC-SHA256 Signature ]

Complete Authentication Flow:

+--------+                 +-------------+                   +---------------+
| Client |                 | API Gateway |                   | Auth Service  |
+--------+                 +-------------+                   +---------------+
    |                             |                                  |
    | 1. POST /auth/login         |                                  |
    |    (credentials in body)    |                                  |
    |---------------------------->|                                  |
    |                             | 2. Forward to Auth Service       |
    |                             |--------------------------------->|
    |                             |                                  | 3. Verify BCrypt
    |                             |                                  |    hash & build JWT
    |                             | 4. Return token response         |
    |                             |<---------------------------------|
    | 5. Return JSON with token   |                                  |
    |<----------------------------|                                  |
    |                                                                |
    | 6. GET /users (Header: "Authorization: Bearer <token>")       |
    |---------------------------->|                                  |
    |                             | 7. JwtAuthenticationFilter:      |
    |                             |    - Verifies HMAC signature     |
    |                             |    - Verifies expiration date    |
    |                             |    - Populates SecurityContext   |
    |                             | 8. If valid, routes to:          |
    |                             |    USER-SERVICE                  |
    | 9. HTTP 200 OK (Data)       |                                  |
    |<----------------------------|                                  |

Token Enforcement Rules:

  • Public Endpoints (No JWT required):
    • POST /auth/register
    • POST /auth/login
    • GET /actuator/health
    • GET /gateway
    • GET /gateway/status
  • Protected Endpoints (Valid JWT required):
    • /users/**
    • /courses/**
    • /enrollments/**
    • /payments/**

Error Responses:

  • Missing Token: HTTP 401 Unauthorized $\rightarrow$ "JWT token is required"
  • Invalid Signature / Malformed Token: HTTP 401 Unauthorized $\rightarrow$ "Invalid or expired JWT token"
  • Expired Token: HTTP 401 Unauthorized $\rightarrow$ "Invalid or expired JWT token"
  • Valid Token: Request proceeds and returns requested data (HTTP 200 OK).

Schema Definitions

1. auth_users Table (academiax_auth_db)

Stores authentication identities and BCrypt-hashed credentials.

Column Data Type Constraints Description
id BIGINT Primary Key, Auto-Increment Unique auth user identifier
username VARCHAR(255) Unique, Not Null Unique login handle / username
password VARCHAR(255) Not Null BCrypt hashed password
role VARCHAR(255) Not Null User authority (STUDENT, INSTRUCTOR, ADMIN)

2. users Table (academiax_user_db)

Stores academic profile records.

Column Data Type Constraints Description
id BIGINT Primary Key, Auto-Increment Unique user profile record ID
name VARCHAR(255) Not Null Full legal name of student or faculty
email VARCHAR(255) Unique, Not Null Institutional email address
phone VARCHAR(255) Optional Contact telephone number
role VARCHAR(255) Not Null Profile classification (STUDENT or INSTRUCTOR)
department VARCHAR(255) Optional Department affiliation (e.g., "Computer Science")
student_id VARCHAR(255) Optional Official campus student identifier (e.g., "STU-101")
instructor_id VARCHAR(255) Optional Official campus instructor identifier

Stores the university course catalog.

Column Data Type Constraints Description
id BIGINT Primary Key, Auto-Increment Unique course ID
title VARCHAR(255) Not Null Official course title
instructor VARCHAR(255) Not Null Assigned instructor name
capacity INTEGER Not Null Maximum allowed enrollments for this course

4. enrollments Table (academiax_enrollment_db)

Maintains active course enrollments.

Column Data Type Constraints Description
id BIGINT Primary Key, Auto-Increment Unique enrollment record ID
student_id BIGINT Not Null Foreign reference to student profile
course_id BIGINT Not Null Foreign reference to course catalog
status VARCHAR(255) Not Null Status flag (ENROLLED, CONFIRMED, CANCELLED)

5. payments Table (academiax_payment_db)

Maintains student tuition ledgers.

Column Data Type Constraints Description
id BIGINT Primary Key, Auto-Increment Unique payment invoice ID
enrollment_id BIGINT Not Null Associated enrollment reference
amount NUMERIC(10,2) Not Null Tuition fee amount (default: $500.00)
payment_status VARCHAR(255) Not Null Payment state (PENDING, COMPLETED, FAILED)

13. User Service Details

The User Service manages institutional student and instructor profiles.

  • Internal Layering:
    • User: JPA Entity mapped to table users.
    • UserRepository: Spring Data JPA repository interface extending JpaRepository<User, Long>.
    • UserService: Encapsulates business validation, mapping between entities and DTOs.
    • UserController: Exposes REST CRUD endpoints under /users.
    • UserRequest & UserResponse: Data Transfer Objects isolating database representation from client contracts.
    • GlobalExceptionHandler: Intercepts ResourceNotFoundException and returns clean 404 Not Found.

  • GET /users – List all profiles.

15. Enrollment Service (Core Business Workflow)

The Enrollment Service orchestrates the central academic registration workflow. It does not operate in isolation—it relies on declarative inter-service communication via Spring Cloud OpenFeign.

[ Client ]
    |
    v (POST /enrollments with Bearer JWT)
[ API Gateway (8080) ]
    |
    v (Validated & Forwarded)
[ Enrollment Service (8084) ]
    |
    +---> [ OpenFeign: CourseClient.getCourseById(courseId) ]
    |           |
    |           v
    |     [ Course Service (8083) ]
    |     - Checks if course exists
    |     - Returns course details (including capacity)
    |
    +---> [ EnrollmentRepository.countByCourseId(courseId) ]
    |     - Counts current active enrollments
    |     - IF (currentCount >= course.capacity):
    |           ABORT! Throw IllegalStateException ("Course has reached maximum capacity")
    |
    +---> [ Persist Enrollment Record: Status = "ENROLLED" ]
    |
    +---> [ OpenFeign: PaymentClient.processPayment(...) ]
                |
                v
          [ Payment Service (8085) ]
          - Automatically creates Tuition Invoice
          - Amount: $500.00 (Configurable)
          - Status: "PENDING"

Why OpenFeign?

Instead of writing verbose HTTP client code (RestTemplate or HttpClient) with URL concatenation and JSON serialization, OpenFeign allows developers to declare a Java interface with Spring MVC annotations:

@FeignClient(name = "COURSE-SERVICE")
public interface CourseClient {
    @GetMapping("/courses/{id}")
    CourseClientResponse getCourseById(@PathVariable("id") Long id);
}

Spring automatically creates the dynamic proxy and seamlessly integrates with Eureka for client-side load balancing.

Sample Input (POST /enrollments):

{
  "studentId": 1,
  "courseId": 1
}

Sample Output (HTTP 200 OK):

{
  "id": 1,
  "studentId": 1,
  "courseId": 1,
  "status": "ENROLLED"
}

In AcademiaX, inter-service communication is strictly declarative:

+----------------------------------------------------------------------+
|                         ENROLLMENT SERVICE                           |
|                                                                      |
|  @FeignClient(name = "COURSE-SERVICE")                               |
|  public interface CourseClient {                                     |
|      @GetMapping("/courses/{id}")                                    |
|      CourseClientResponse getCourseById(@PathVariable("id") Long id);|
|  }                                                                   |
|                                                                      |
|  @FeignClient(name = "PAYMENT-SERVICE")                              |
|  public interface PaymentClient {                                    |
|      @PostMapping("/payments")                                      |
|      PaymentClientResponse processPayment(                           |
|          @RequestBody PaymentClientRequest request);                 |
|  }                                                                   |
+----------------------------------------------------------------------+
               |                                       |
     HTTP GET via Eureka                     HTTP POST via Eureka
               v                                       v
      +------------------+                   +-------------------+
      |  COURSE-SERVICE  |                   |  PAYMENT-SERVICE  |
      +------------------+                   +-------------------+

Advantages of OpenFeign in AcademiaX:

  1. Zero Boilerplate: No need to manually manage HTTP connections or status code parsing.
  2. Built-in Service Discovery: Direct integration with Eureka allows Feign to resolve COURSE-SERVICE to an active IP address automatically.
  3. Resilience: If one instance of Course Service is down, the load balancer directs the Feign request to an active instance.

18. Complete End-to-End Business Flow

Here is a step-by-step trace of a complete student enrollment lifecycle:

  1. User Registration:
    • A student registers credentials through the Gateway: POST http://localhost:8080/auth/register.
    • Auth Service hashes the password using BCrypt and saves the record in academiax_auth_db.
  2. User Login:
    • The student logs in: POST http://localhost:8080/auth/login.
    • Auth Service verifies credentials and issues a cryptographic JWT valid for 7 days.
  3. Profile Creation:
    • The student creates their academic profile: POST http://localhost:8080/users using Authorization: Bearer <JWT>.
  4. Course Catalog Definition:
    • An administrator creates a course: POST http://localhost:8080/courses with capacity: 30.
  5. Course Enrollment & Validation:
    • The student submits an enrollment request: POST http://localhost:8080/enrollments with courseId: 1.
    • The Gateway checks the JWT, extracts claims, and routes the request to Enrollment Service.
    • Enrollment Service queries Course Service via Feign: Course 1 exists? Yes. Capacity? 30.
    • Enrollment Service counts current enrollments in academiax_enrollment_db: 0 currently enrolled.
    • Seat check passes (0 < 30).
    • Enrollment record is created with status ENROLLED.
  6. Automatic Tuition Invoicing:
    • Enrollment Service immediately calls Payment Service via Feign.
    • Payment Service records a tuition fee of $500.00 in status PENDING linked to enrollmentId: 1.
  7. Tuition Settlement:
    • The student pays tuition: PUT http://localhost:8080/payments/1 updating status to COMPLETED.

21. Error Handling Architecture

AcademiaX implements centralized exception handling via @RestControllerAdvice (GlobalExceptionHandler) in microservices:

  1. 401 Unauthorized (Perimeter Security Failure):
    • Trigger: Client omits Authorization header or supplies an invalid/expired token.
    • Handled By: JwtAuthenticationFilter in API Gateway.
    • Output: "JWT token is required" or "Invalid or expired JWT token".
  2. 404 Not Found (Resource Missing):
    • Trigger: Client requests an entity ID that does not exist in the database (e.g., GET /users/99999).
    • Handled By: GlobalExceptionHandler intercepting ResourceNotFoundException.
    • Output: {"timestamp": "...", "status": 404, "error": "Not Found", "message": "User not found with id: 99999"}.
  3. 400 Bad Request (Business Rule Violation / Capacity Exceeded):
    • Trigger: Student attempts to enroll in a course whose active enrollment count equals or exceeds capacity.
    • Handled By: GlobalExceptionHandler in Enrollment Service intercepting IllegalStateException.
    • Output: {"timestamp": "...", "status": 400, "error": "Bad Request", "message": "Course has reached maximum capacity"}.

25. Practical Advantages of the Implemented Architecture

  1. High Fault Isolation: Failure in the payment gateway or user reporting modules does not crash the enrollment portal.
  2. Independent Scalability: During course registration rush hours, multiple instances of enrollment-service and api-gateway can run concurrently without wasting hardware on idle services.
  3. Decoupled Data Storage: Each service owns its schema. Schema modifications to course fields do not impact user or auth database tables.
  4. Declarative Feign Calls: Simplified, maintainable inter-service communication without raw HTTP boilerplate.
  5. Robust Perimeter Defense: Centralized JWT verification at the Gateway guarantees that downstream microservices receive only authenticated requests.

26. Current Project Limitations

To maintain academic rigor and transparency, the following design boundaries are noted:

  1. Synchronous Inter-Service Calls: Enrollment uses synchronous HTTP via OpenFeign. If Course Service experiences latency, the enrollment call waits synchronously. (Can be enhanced with asynchronous messaging using Kafka/RabbitMQ).
  2. Local JWT Verification: The Gateway verifies tokens using a shared symmetric HMAC secret key rather than an asymmetric public/private key pair (RSA/ECDSA).
  3. No Distributed Transaction Rollback (Saga): If payment creation fails after enrollment is persisted, manual reconciliation or a Saga orchestrator is needed to compensate the transaction.

27. Future Enhancements

The following features are identified as high-value roadmap items for subsequent versions:

  • Role-Based Access Control (RBAC): Fine-grained method security (@PreAuthorize("hasRole('ADMIN')")) differentiating student self-service from faculty administrative actions.
  • Event-Driven Messaging: Introducing Apache Kafka or RabbitMQ for asynchronous event broadcasting (e.g., EnrollmentCreatedEvent triggers notifications and billing asynchronously).
  • External Payment Gateway: Integration with Stripe or PayPal SDK for real-time credit card and net-banking settlements.
  • Automated Notification Service: Microservice sending automated SMS and email confirmations upon successful registration.
  • Distributed Tracing & Monitoring: Implementing Zipkin and Micrometer for end-to-end request latency tracing across microservice boundaries.

28. Conclusion

AcademiaX successfully demonstrates a modern, enterprise-grade distributed solution for higher education course enrollment and tuition billing. By utilizing Java 25, Spring Boot 4.1.1, Spring Cloud 2025.1.3, and PostgreSQL 18, the project demonstrates how microservices solve the availability, scalability, and security shortcomings of legacy monolithic systems.

Through real-time capacity checks via OpenFeign, perimeter security enforcement via Spring Cloud Gateway and 7-day JWTs, dynamic discovery via Netflix Eureka, and decoupled PostgreSQL schemas, AcademiaX delivers a scalable, resilient, and production-ready architectural foundation.

29. Faculty Viva / Demo Questions & Answers

Q1: Why did you choose a Microservices architecture instead of a Monolith?

Answer: A monolith couples all features into a single codebase and database. During peak enrollment, high traffic on course registration can crash the entire monolith. Microservices provide fault isolation, independent scaling, and autonomous databases, ensuring critical operations remain available.

Q2: What is the role of the Eureka Server?

Answer: Eureka serves as the centralized service discovery registry. Microservices dynamically register their network location (IP and port) under a logical service name (e.g., COURSE-SERVICE). The API Gateway and Feign clients query Eureka to locate services without hardcoding hostnames.

Q3: Why is an API Gateway necessary?

Answer: The Gateway acts as the single secure entry point (port 8080) for all client applications. It centralizes routing, performs client-side load balancing, and enforces JWT security, preventing external clients from directly accessing internal microservice ports.

Q4: Why did you use JWT for authentication?

Answer: JWT enables stateless authentication. The server does not need to store active session IDs in memory or a database. The token contains cryptographically signed claims (username, role, expiration) that the Gateway validates instantly using HMAC-SHA256.

Q5: Why does each microservice have its own separate database?

Answer: To enforce the Database-per-Service pattern. This prevents loose coupling, eliminates table-locking interference between services, and ensures true microservice autonomy where each team owns its schema.

Q6: What is OpenFeign and where is it used in your project?

Answer: OpenFeign is a declarative HTTP web service client. In our project, Enrollment Service uses Feign interfaces to synchronously call Course Service (to verify course validity and capacity) and Payment Service (to automatically generate a tuition invoice).

Q7: What happens behind the scenes when a student enrolls in a course?

Answer: The client sends POST /enrollments with a JWT to the Gateway. The Gateway validates the token and forwards the request to Enrollment Service. Enrollment Service uses Feign to fetch course capacity from Course Service, verifies that current enrollments do not exceed the limit, persists the enrollment, and calls Payment Service via Feign to generate a pending $500.00 tuition invoice.

Q8: How is course capacity checked to prevent overbooking?

Answer: Before saving an enrollment, Enrollment Service retrieves the course's capacity from Course Service via Feign and queries its local repository with countByCourseId(courseId). If the current count is equal to or greater than the capacity, it throws an IllegalStateException, returning HTTP 400 Bad Request.

Q9: How is a tuition payment record created?

Answer: Upon successful enrollment persistence, Enrollment Service invokes PaymentClient.processPayment(...) passing the enrollmentId and default tuition amount ($500.00). Payment Service records this as a new entry with status PENDING.

Q10: What happens if a client accesses /users without a JWT?

Answer: The Gateway's JwtAuthenticationFilter intercepts the request, detects that the Authorization header is missing or lacks the Bearer prefix, immediately halts execution, and responds with HTTP 401 Unauthorized and message "JWT token is required".

Q11: What happens if a client passes a tampered or invalid JWT?

Answer: The Gateway attempts to parse and verify the signature using the shared secret key. If the signature or structure is invalid, JJWT throws a JwtException, which is caught to return HTTP 401 Unauthorized with message "Invalid or expired JWT token".

Q12: What happens when an expired token is submitted?

Answer: JJWT throws an ExpiredJwtException. The filter catches this exception and responds with HTTP 401 Unauthorized ("Invalid or expired JWT token").

Q13: Why are Data Transfer Objects (DTOs) used?

Answer: DTOs separate internal database entities from external API contracts. This prevents over-posting attacks, avoids exposing sensitive database columns, and decouples internal table schema changes from client-facing JSON contracts.

Q14: What is the purpose of the Spring Data JPA Repository layer?

Answer: It abstracts database operations by providing built-in implementations of standard CRUD queries (e.g., save(), findById(), findAll()) and allows custom derived query methods like countByCourseId() without writing raw SQL.

Q15: How are passwords stored securely in the Auth Service?

Answer: Passwords are never stored in plaintext. Auth Service configures BCryptPasswordEncoder, which applies a cryptographic adaptive one-way hashing algorithm with automatic salting before saving credentials to academiax_auth_db.

Q16: Why did you choose PostgreSQL 18?

Answer: PostgreSQL is an enterprise-grade, ACID-compliant open-source relational database that provides strong data integrity, reliable transactions, and high concurrency for student and financial records.

Q17: What is Spring Cloud Gateway Server Web MVC?

Answer: It is the modern synchronous Spring Cloud Gateway implementation built on Spring MVC and the Tomcat servlet container. It uses router functions (GatewayRouterFunctions) and standard servlet filters, making it straightforward to maintain and integrate with Spring Security.

Q18: What is client-side load balancing?

Answer: Instead of relying on a dedicated hardware load balancer, the client (or Gateway) queries Eureka for all available instances of a target service and uses Spring Cloud LoadBalancer to distribute requests evenly among healthy instances.

Q19: What is the configured expiration duration of the JWT in AcademiaX?

Answer: Exactly 7 days (604,800,000 milliseconds), configured in JwtService.java.

Q20: Can you summarize the entire flow in one sentence?

Answer: A client authenticates via Auth Service to receive a 7-day JWT, routes through API Gateway to Enrollment Service, which validates course capacity via Course Service and initiates tuition billing via Payment Service using OpenFeign, with all services discovered dynamically through Eureka and backed by dedicated PostgreSQL databases.
